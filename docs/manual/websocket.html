WebSocket (servidor propio)

Conexion permanente con tu servidor (MMO, chat, lobby): mensajes en los dos sentidos, reconexion y seguridad.

En esta página

WebSocket abre una conexión permanente con tu servidor (el backend de un MMO, un chat, un lobby, notificaciones en directo): los dos lados se mandan mensajes cuando quieren, sin pedir y esperar como con Http. Conectar, enviar y cerrar nunca paran el juego: cada conexión trabaja en segundo plano y los mensajes llegan en el hilo del juego, al principio del frame, como un update más. Si se corta, se reconecta sola. 

WsClient ws_;   // miembro del script

void start() override {
    ws_.connect(Value{{"url", "wss://juego.miservidor.com/ws"}, {"name", "mmo"},
                      {"headers", Value{{"Authorization", "Bearer " + token}}}});
    ws_.onOpen([](const Value&) { Debug::log("conectado"); });
    ws_.onMessage([this](const Value& ev) {
        if (ev["data"]["tipo"].asString() == "chat") mostrarChat(ev["data"]["texto"].asString());
    });
    ws_.onClose([](const Value& ev) { Debug::log("cerrada: " + ev["code"].asString()); });
}

void enviarChat(const std::string& texto) {
    ws_.sendJson(Value{{"tipo", "chat"}, {"texto", texto}});
}

WebSocket, Http o Network

Para quéCómo
HttpPedir algo y esperar la respuesta: iniciar sesión, leer el marcador, guardar en la nube, noticias.Una petición, una respuesta. HTTPS.
WebSocketEstar conectado a tu servidor todo el rato: MMO, chat, lobby, emparejamiento, avisos en directo, juegos por turnos.Una conexión TCP abierta (ws:// o wss://); mensajes en los dos sentidos, en orden, sin perderse.
NetworkPartidas en tiempo real entre jugadores (uno hace de servidor, o CramionServer): objetos y variables sincronizados.UDP (ENet), mensajes fiables o rápidos.

Un MMO típico usa los tres: Http para la cuenta, WebSocket para el chat, el lobby y el mundo persistente, y Network para una partida concreta.

Conectar, enviar y recibir

WebSocket::connect(opciones) devuelve el id de la conexión al momento (o vacío si la dirección no vale; el motivo sale en la Consola) y conecta en segundo plano. Hasta que llega el evento open no se puede enviar. Los mensajes se reciben de dos formas (en cada conexión, una u otra, nunca las dos):

  • Escuchas (on): una función por tipo de evento; el motor la llama al principio del frame.
  • poll: tú pides los eventos pendientes cuando quieras (por ejemplo cada frame en update). Si una conexión no tiene escuchas, sus eventos se guardan hasta que hagas poll.
// Con escuchas (WebSocket::* directo, sin WsClient)
const Value id = WebSocket::connect(Value{{"url", "ws://localhost:8080/juego"}});
WebSocket::on(id, "message", [](const Values& a) {
    const Value& ev = a[0];
    Debug::log("llego: " + ev["text"].asString());
});
WebSocket::on(id, "open", [id](const Values&) { WebSocket::send(id, "hola"); });

// Con poll (mejor con mucho trafico: un solo viaje al motor por frame)
void update(float) override {
    for (const Value& ev : ws_.poll()) {
        const std::string tipo = ev["type"].asString();
        if (tipo == "message") procesar(ev);
        else if (tipo == "close") Debug::log("cerrada");
    }
}

El evento

ev["type"]Campos (además de id y name)
openprotocol: el subprotocolo que eligió el servidor (o vacío).
message (texto)binary = false, text y, si el texto es JSON (empieza por { o [, hasta 1 MB), data ya decodificado.
message (binario)binary = true y base64 con los bytes.
closecode (1000 normal, 1001 se va, 1006 cortada sin cierre, 4000-4999 los tuyos), reason, clean (hubo saludo de cierre), reconnect (detrás viene una reconexión) y dropped (mensajes tuyos que no se llegaron a enviar).
errorerror (texto en español, tabla de abajo), status (HTTP del saludo, 401, 404...; 0 si no hubo) y reconnect.
reconnectingattempt (1, 2...) y delay (segundos hasta el intento).

Con on(id, "any", fn) recibes todos. on devuelve un número para dejar de escuchar con WebSocket::off(numero). on acepta el id o el nombre de la conexión, incluso antes de que exista.

Visual Scripting

El nodo On WebSocket (grupo Eventos) escucha una conexión por su nombre (Conexion, main por defecto) y un tipo (Tipo: message, open, close, error, reconnecting o any). Sus salidas: Evento (el objeto entero), Texto (el mensaje, o el error, o el motivo del cierre) y Datos (el JSON decodificado). Para conectar, en Event Start pon el nodo WebSocket.connect con la tabla {url = "wss://...", name = "main"}; como conectar con nombre devuelve la conexión que ya existe, es seguro hacerlo en cada carga de escena. Para enviar, el nodo WebSocket.send con el nombre como id.

En el servidor dedicado

Los scripts de CramionServer (Windows y Linux) usan la misma API: un servidor de partida puede avisar a tu backend (resultado de la partida, jugadores que entran) por WebSocket mientras los jugadores juegan por Network.

Conexiones con nombre y cambio de escena

Con name la conexión es del juego, no de la escena:

  • Sobrevive al cambio de escena (Scene::load). Las que no tienen nombre se cierran (1001).
  • Llamar a connect con un nombre que ya está vivo devuelve la misma conexión (no abre otra). Así cada escena puede conectar sin miedo.
  • WebSocket::find("mmo") da su id, y WsClient::attach("mmo") la recupera.
  • Al cambiar de escena las escuchas (on) se quitan, porque eran de los scripts de la escena vieja; los mensajes que lleguen mientras tanto se guardan hasta que vuelvas a escuchar o hagas poll.
void awake() override {
    if (!ws_.attach("mmo"))   // primera escena: aun no existe
        ws_.connect(Value{{"url", "wss://juego.miservidor.com/ws"}, {"name", "mmo"}});
    ws_.onMessage([this](const Value& ev) { procesar(ev); });
}

Recarga en caliente

Al guardar el .cpp en Play (o si el proceso de los scripts se reinicia tras un fallo) la conexión sigue abierta, pero las escuchas de C++ se olvidan: sus funciones eran del proceso anterior. Vuelve a ponerlas en onAfterReload: 

void onAfterReload(const Value&) override {
    ws_.attach("mmo");
    ws_.onMessage([this](const Value& ev) { procesar(ev); });
}

Las escuchas de los Visual Scripts no se pierden.

Reconexión

Si la conexión se corta (1006, el servidor se reinicia con 1001/1012, sin Internet un rato, el móvil cambia de red) el motor vuelve a conectar solo, esperando cada vez más (0,5 s, 1 s, 2 s... hasta 30 s, con algo de azar para que no vuelvan todos los jugadores a la vez). Recibes close (o error) con reconnect = true, después reconnecting y, al volver, open otra vez: ahí vuelve a identificarte o a pedir el estado.

No reconecta cuando cierras tú (close), cuando el servidor cierra normal (1000) o por un error del protocolo (1002, 1003, 1007, 1008, 1009, 1010), ante un rechazo de la sesión (HTTP 401, 403, 404 y otros 4xx) ni con tus códigos 4000-4999 (salvo appCodes = true): así un servidor que te echa (4001 "baneado") o un token caducado no se convierten en un bucle de intentos. 

ws_.connect(Value{{"url", url}, {"name", "mmo"},
                  {"reconnect", Value{{"min", 1}, {"max", 60}, {"tries", 10}, {"appCodes", false}}}});

// Renovar el token antes del proximo intento
ws_.onReconnecting([this](const Value&) {
    WebSocket::setHeader(ws_.id(), "Authorization", "Bearer " + tokenNuevo());
});

reconnect = false la desactiva. Lo que quedó sin enviar al cortarse se tira (cuenta en dropped), salvo con resend = true.

Binario

Los bytes cruzan entre el motor y los scripts en base64 (nunca en bruto). WsClient::sendBinary codifica por ti; lo que llega trae ev["base64"]: 

ws_.sendBinary(paquete);   // std::string con bytes
ws_.onMessage([](const Value& ev) {
    if (!ev["binary"].asBool()) return;
    std::string bytes;
    if (base64Decode(ev["base64"].asString(), bytes)) leerPaquete(bytes);
});

base64Encode y base64Decode del SDK no llaman al motor. Base64::encode y Base64::decode hacen lo mismo desde la API (Visual Scripting).

Mucho tráfico

  • Usa poll en update: un viaje al motor por frame, con todos los eventos juntos. Las escuchas cuestan un viaje por evento.
  • Cada frame se entregan como mucho net.WsMaxEventsPerFrame eventos (512) a las escuchas; el resto espera al frame siguiente, sin perderse.
  • Si los scripts no recogen, la cola de entrada se llena (16 MB) y el motor deja de leer del servidor hasta que haya sitio: no se pierde nada y la memoria no crece (TCP frena al servidor).
  • Junta mensajes pequeños: es mejor un mensaje con 20 posiciones que 20 mensajes.

WebSocket::close(id, codigo, motivo)Cierre limpio (1000, o tus códigos 3000-4999; motivo de hasta 123 bytes). No reconecta.
WebSocket::closeAll(codigo, motivo)Cierra todas.

WsClient (en el SDK, sin incluir nada) envuelve todo esto: connect, attach, send, sendJson, sendBinary, close, state, poll y onOpen/onMessage/onClose/onError/onReconnecting. Al destruirse quita sus escuchas pero no cierra la conexión. Referencia completa en WebSocket (C++).

Seguridad

  • Usa wss:// (TLS 1.2 o 1.3): se comprueban el certificado del servidor y su nombre. Si está caducado, es de otro dominio o no es de una autoridad de confianza, no se conecta (y no lo reintenta).
  • ws:// sin cifrar solo va a localhost / 127.0.0.1, para probar en tu PC. Con net.WsInsecure = 1 también a la red local (10.x, 172.16-31.x, 192.168.x), comprobado con las direcciones ya resueltas; 2 (cualquiera) solo con trucos activados.
  • Las cabeceras no pueden llevar saltos de línea ni ser las del protocolo (Host, Upgrade, Connection, Sec-WebSocket-*, Content-Length).
  • Cada mensaje tiene un tamaño máximo (se comprueba al llegar cada trozo, antes de reservar memoria) y las colas de entrada y salida tienen tope: un servidor que manda datos sin fin no llena la memoria.
  • Conectar, enviar y cerrar nunca bloquean el juego; un servidor que no responde se da por muerto con los tiempos máximos (conectar, enviar, cerrar, sin datos).
  • El texto que llega se comprueba como UTF-8; el binario nunca cruza al script en bruto.

No pongas claves secretas en los scripts: van dentro del juego exportado. Identifica al jugador con un token que le dé tu servidor al iniciar sesión (por Http) y mándalo en Authorization. Tu servidor debe comprobar todo lo que llega: el cliente puede estar modificado.

Tu servidor

  • Cualquier servidor WebSocket estándar (RFC 6455) vale: Node (ws), Go, Python (websockets), C#, Rust...
  • Manda un ping como mucho cada 20 s o algo de tráfico: muchos proxies y routers cortan una conexión callada.
  • Para echar o rechazar, cierra con tus códigos 4000-4999 y un motivo: el juego los recibe en close y no reconecta.
  • Sin compresión (permessage-deflate): desactívala en el servidor.
  • Para publicar, pon delante un HTTPS (Let's Encrypt, Nginx, Caddy, Cloudflare) y usa wss://.
// Node: npm install ws
const { WebSocketServer } = require("ws");
const wss = new WebSocketServer({ port: 8080, perMessageDeflate: false });

wss.on("connection", (ws, req) => {
  const token = (req.headers.authorization || "").replace("Bearer ", "");
  if (!tokenValido(token)) return ws.close(4001, "token no valido");
  ws.isAlive = true;
  ws.on("pong", () => (ws.isAlive = true));
  ws.on("message", (data, isBinary) => {
    if (isBinary) return;
    const msg = JSON.parse(data);
    if (msg.tipo === "chat")
      for (const c of wss.clients) c.send(JSON.stringify({ tipo: "chat", texto: msg.texto }));
  });
});

// Ping cada 20 s; la que no conteste, fuera
setInterval(() => {
  for (const ws of wss.clients) {
    if (!ws.isAlive) { ws.terminate(); continue; }
    ws.isAlive = false;
    ws.ping();
  }
}, 20000);

En el juego: ws://localhost:8080 mientras pruebas y wss://tu-dominio al publicar.

PlataformaNotas
Windows (editor, juego, servidor)WinHTTP: usa el proxy del sistema y su almacén de certificados. Responde solo a los pings del servidor y manda keepalive, pero no mide el rtt (sale -1) ni da por muerta una conexión callada salvo con idleTimeout o heartbeat.

Linux (CramionServer)ws:// siempre. wss:// necesita OpenSSL al compilar (sudo apt install libssl-dev, opción CRAMION_WITH_OPENSSL, activada por defecto); sin él, wss:// da un error claro.
